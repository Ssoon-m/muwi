# 동작 원리

muwi가 왜 이렇게 만들어졌고, 어떤 방식으로 진행을 기록하고 보여 주는지 설명합니다. muwi를 쓰는 데 꼭 필요한 내용은 아닙니다. 기록을 얼마나 믿어도 되는지 판단하거나 muwi를 고칠 때 읽으세요.

## 해결하려는 문제

AI에게 일을 맡기는 흔한 방법은 순서를 정해 주는 것입니다. "요구사항을 읽고, 계획을 승인받고, 구현하고, 리뷰한다"를 skill이나 워크플로우로 적어 두는 방식입니다.

이 방식에는 두 가지 문제가 있습니다.

- 정해 둔 순서는 지금 모델의 약점에 맞춘 것입니다. 모델이 좋아지면 그 순서가 더 나은 판단을 막습니다.
- 작은 일에도 큰 일의 순서를 그대로 따라야 합니다.

순서를 정하지 않으면 다른 문제가 생깁니다. AI가 무엇을 하고 있는지 보이지 않고, 결과가 이상할 때 어디서 잘못됐는지 찾기 어렵습니다.

muwi는 순서는 AI에게 맡기고, 대신 진행을 보이게 하고 원인을 찾을 수 있게 합니다.

| | 순서를 정해 두는 방식 | muwi |
| --- | --- | --- |
| 순서 | 사람이 미리 정합니다 | AI가 작업마다 정합니다 |
| 순서에서 벗어나면 | 막습니다 | 막지 않고 기록에 남깁니다 |
| 결과가 이상할 때 | 순서를 고칩니다 | skill, 지침, 훅을 고칩니다 |
| 모델이 좋아지면 | 순서를 다시 써야 합니다 | 그대로 씁니다 |
| 약한 점 | 일에 맞지 않는 순서도 따릅니다 | AI가 기록을 제때 남기지 않으면 알 수 있는 것이 줄어듭니다 |

## 구성 요소

AI가 일하면서 진행을 파일에 적고, 보기(그래프 칸)가 그 파일을 읽어 그립니다. 기록하고 판단하는 일은 모두 코어가 합니다. 멀티플렉서와 이야기하는 일은 터미널 연결이, 그리는 일은 보기가 맡습니다.

```
사용자 ──"PROJ-123 작업해줘"──▶ Claude Code 세션
                                   │
                    ┌──────────────┴───────────────┐
                    │ AI가 실행: muwi plan, muwi node │  계획과 진행을 적어요
                    │ 훅이 관찰: skill 읽음, 서브에이전트 │  AI가 적지 않는 사실을 적어요
                    └──────────────┬───────────────┘
                                   ▼
                    ~/.muwi/<작업>/plan.json, events.jsonl
                                   │
                                   ▼
                    보기: Herdr 앱의 그래프 칸 (muwi board로 읽어요)
```

| 요소 | 하는 일 |
| --- | --- |
| `muwi` 명령 | AI가 실행하면 계획과 진행이 파일에 기록됩니다 |
| 지침 | 세션이 시작될 때 훅이 AI에게 계획을 적는 방법을 알려 줍니다 |
| 훅 | AI가 스스로 적지 않는 사실(읽은 skill, 서브에이전트, 세션이 일하는지 끝났는지)을 기록합니다 |
| 커넥터 | AI 도구마다 훅의 모양이 다릅니다. 도구별 커넥터가 그 도구의 훅 입력을 muwi의 공통 사건(세션 시작, 사람이 말함, 고치려 함, skill을 읽음 …)으로 바꾸고, muwi의 답을 그 도구의 형식으로 돌려줍니다. 기록하는 쪽은 도구를 모릅니다 |
| 터미널 연결 | 세션들이 도는 멀티플렉서(Herdr 등)와 이야기합니다. 이 터미널의 주소, 살아 있는 터미널 목록, 띄우기, 글 보내기, 화면 읽기, 닫기, 놓기만 합니다. 무엇을 띄우고 무엇을 적을지는 코어가 정합니다 |
| 보기 | 기록을 읽어 작업 목록과 그래프로 그립니다 (Herdr 앱의 그래프 칸). 기록이 바뀌면 다시 그립니다. 세션 기록의 터미널 주소로 세션과 작업을 이어서, 지금 보는 터미널의 작업을 보여 주고 계획 없이 일하는 세션도 목록에 넣습니다. 기록을 바꾸지 않습니다 |

## 터미널 연결과 보기

코어는 어느 멀티플렉서나 앱을 쓰는지 모릅니다. 둘 다 규격(`packages/core/src/plugins.ts`)을 따르는 모듈이고, `muwi setup`이 적어 둔 경로(또는 `$MUWI_TERMINALS`, `$MUWI_VIEWS`)에서 불러옵니다. 둘 다 없어도 계획과 진행 기록, `muwi show`·`status`는 그대로 됩니다.

| 터미널 연결이 하는 일 | 쓰는 곳 | 없으면 |
| --- | --- | --- |
| `place`: 이 프로세스가 도는 터미널 | 세션과 터미널을 잇기. 세션 id를 주지 않는 도구의 세션 이름 | 터미널을 모릅니다 |
| `list`: 살아 있는 터미널과 에이전트 상태 | 세션이 닫혔는지, 지금 무얼 하는지 | 훅이 알려 준 것만 씁니다 |
| `launch`, `send`, `read`, `close` | `muwi run`·`tell`·`peek`·`tidy`·`resume` | 새 세션에 맡길 수 없습니다 |
| `arrange`: 옆 칸·아래 칸·새 탭에 놓기 | 계획의 `show` | 놓지 않고 띄웁니다 |

| 보기가 하는 일 | 쓰는 곳 |
| --- | --- |
| `commands`, `help` | 보기가 더하는 명령 (Herdr 앱은 `muwi layout`, `muwi open`) |
| `config` | `muwi config` |
| `board` | `muwi board`에 더할 값 |
| `setup`, `remove` | `muwi setup`이 넣고 뺄 것 (그래프 칸 등) |

다른 멀티플렉서(tmux, 직접 만든 것 등)를 쓰려면 이 규격의 터미널 연결을 만들어 붙이면 됩니다. `@muwi/herdr`의 `src/terminals.ts`가 예입니다.

## 작업 하나의 흐름

```
사용자: PROJ-123 작업해줘

① AI가 실행:  muwi plan --work shop-web-PROJ-123 --request "…" '{"nodes":[…]}'
   → plan.json이 생기고, 그래프 칸에 카드가 그려져요
② AI가 실행:  muwi node read start
   → [티켓·기획 읽기] 카드가 "작업 중"이 돼요
   → plan.json의 그 노드에 "지금 하고 있는 쪽: 이 세션, 1회차"가 적혀요
③ AI가 skill을 읽어요
   → 훅이 plan.json에서 "이 세션이 read를 하는 중"임을 확인하고,
     events.jsonl에 "skill 읽음 · read 1회차"를 남겨요
④ AI가 실행:  muwi node read done "요구사항 2건"
   → 카드가 "끝"이 돼요
⑤ AI가 구현을 새 세션에 맡겨요:  muwi run impl "…" --show pane
   → 터미널 연결이 멀티플렉서에 Claude 세션을 띄우고, 그 세션이 시작하면서 impl 노드에 붙어요
   → 맡긴 세션은 muwi wait으로 기다리고, 맡은 세션은 끝나면 muwi tell로 알려요
⑥ AI가 리뷰를 서브에이전트에 맡겨요
   → 훅이 서브에이전트가 뜬 것과 읽은 skill을 리뷰 노드에 남겨요
⑦ 리뷰에서 문제가 나와서 AI가 다시 실행:  muwi node impl start
   → 같은 카드에 "2회차"가 붙어요. 1회차의 기록은 그대로 남아요
⑧ AI가 실행:  muwi node pr wait "PR 올릴까요?"
   → 카드가 "응답 대기"가 되고, 작업이 목록 맨 위로 올라와요
```

## 일어난 순간에 노드를 함께 기록하는 이유

기록에는 두 종류의 줄이 있습니다. AI가 `muwi` 명령으로 적는 줄과, 훅이 관찰해서 적는 줄입니다.

훅은 기록하는 순간에 그 일이 어느 노드의 몇 번째 회차 것인지 함께 적습니다.

```
AI가 적는 줄    10:00 [브랜치 준비] 시작 · 1회차 · 시작한 쪽: 이 세션
훅이 적는 줄         10:02 skill branch-rule 읽음 → [브랜치 준비] 1회차
                     10:03 서브에이전트가 뜸       → [브랜치 준비] 1회차
```

다른 방법도 있습니다. 훅은 시각만 적고, 그래프를 그릴 때 "그 시각에 하던 노드"를 맞춰 보는 방법입니다. 이 방법은 다음 경우에 틀린 결과를 확신 있게 보여 줍니다.

- 같은 노드를 다시 하면 두 회차의 기록이 섞입니다.
- 서브에이전트가 잠깐 뜨면 그 노드를 서브에이전트가 한 것으로 봅니다.
- 다른 세션이 넘겨받으면 앞 세션이 읽은 skill이 뒤 세션에 붙습니다.

그래서 muwi는 그래프를 그릴 때 추측하지 않고 기록된 대로만 보여 줍니다. 확실하지 않은 것은 그렇게 표시합니다.

| 표시 | 뜻 |
| --- | --- |
| 확실하지 않음 | 같은 쪽이 노드 여러 개를 동시에 하고 있었습니다. 가장 늦게 시작한 노드에 기록했습니다 |
| 기록 없음 | AI가 일을 마친 뒤에 시작과 끝을 함께 기록했습니다 |
| 볼 수 없었음 | 그 세션에서 훅이 실행되지 않았습니다 |

## 누가 했는지 판단하는 방법

계획의 `run`은 AI가 정한 것이고, 그래프의 표시는 기록된 사실입니다. 둘이 다르면 `≠계획`이 붙습니다.

회차를 한 쪽은 그 회차를 시작한 쪽입니다.

| 누가 | 기록되는 방식 |
| --- | --- |
| 세션이 직접 | 노드 시작 줄에 그 세션이 기록됩니다. 다른 세션이 이어받아도 직접 한 것입니다 |
| 새 세션 | `muwi run`이 띄운 프로그램에 작업 이름과 노드 id를 환경 변수(`MUWI_RUN`, `MUWI_RUN_WORK`, `MUWI_RUN_NODE`)로 넘깁니다. 그 세션의 시작 훅(훅이 없는 도구는 첫 `muwi` 명령)이 읽고 노드에 붙습니다. 그 이름표로 처음 붙은 세션만 맡은 것으로 봅니다 |
| 서브에이전트 | 서브에이전트는 세션 id가 띄운 세션과 같습니다. Claude Code가 훅에 넘겨주는 서브에이전트 id로 구분합니다 |

세션이 노드를 시작해 두고 서브에이전트를 띄우면 다음과 같이 판단합니다.

- 계획에 서브에이전트로 하기로 적은 노드면 서브에이전트가 한 것으로 봅니다.
- 그 밖에는 세션이 직접 한 것으로 보고, 서브에이전트는 "도움"으로 남깁니다.

## 세션이 닫혔는지 아는 방법

muwi는 AI가 적은 것만 압니다. 세션을 닫으면 "끝"을 기록할 쪽이 없습니다. 그래서 기록을 보여 줄 때마다 세 가지를 합쳐 판단합니다 (`packages/core/src/live.ts`).

| 알게 된 것 | 판단 |
| --- | --- |
| 훅이 세션이 끝났다고 알렸습니다 (`SessionEnd`) | 닫혔습니다 |
| 같은 터미널에서 더 늦게 시작한 세션이 있습니다 | 닫혔습니다. 같은 칸에서 다른 세션이 시작됐습니다 (`/clear`, 새로 띄움) |
| 터미널 연결의 목록에 그 터미널이 없습니다 | 닫혔습니다 |
| 터미널은 있는데 에이전트가 실행 중이 아닙니다 | 닫혔습니다 |
| 터미널 연결이 에이전트 상태를 알려 줍니다 | 그 상태(일하는 중, 입력을 기다림, 멈춤)를 씁니다 |
| 터미널 연결은 없고 훅이 알려 줬습니다 (`UserPromptSubmit`, `Stop`) | 사람이 말을 건 뒤면 일하는 중, 말을 끝낸 뒤면 멈춤으로 봅니다 |
| 아무것도 알 수 없습니다 | 판단하지 않습니다 |

닫힌 세션이 하던 노드는 "세션이 닫힘"으로 표시하고, 기록 파일은 고치지 않습니다.

## muwi는 막지 않습니다

muwi는 AI가 하려는 일을 막지 않습니다. 순서를 확인하지 않아서 앞 노드가 끝나지 않아도 다음 노드를 시작할 수 있고, 결과의 형식도 확인하지 않습니다. 계획이 없어도 파일을 고칠 수 있고, push나 PR 앞에서 묻지도 않습니다.

계획을 적을지는 AI가 일의 크기를 보고 정합니다. 파일을 고치는지가 아니라 단계가 여럿인지를 봅니다. PR 리뷰나 여러 곳을 살피는 조사도 단계가 여럿이면 계획을 적고, 질문에 바로 답하기나 오타 하나 고치기처럼 한 번에 끝나는 일은 적지 않습니다. 계획을 적지 않았다면 작은 일이라고 본 것입니다. 작게 시작한 일이 커지면 그때 적습니다.

0.5.x까지는 계획 없이 파일을 고치려 하면 훅이 한 번 돌려보냈습니다 (계획 알림). 파일을 고치는지로는 일의 크기를 알 수 없어서 0.6.0에서 뺐습니다. 계획 없이 일하는 세션은 목록의 "열린 대화"에 보입니다.

계획은 방향 있는 선으로 이어진 그래프입니다. `muwi add`에 자리를 주지 않으면 맨 끝 노드 뒤에 잇고, 계획에 어느 노드와도 이어지지 않은 노드가 있으면 알려 줍니다.

## 훅이 하는 일

훅은 관찰만 합니다. 아무것도 막지 않고, 훅이 없어도 계획과 진행 기록은 그대로 됩니다 (에이전트가 `muwi` 명령으로 직접 적습니다). Claude Code 커넥터(`muwi setup --tool claude`)는 `~/.claude/settings.json`에 다음 훅을 겁니다. 다른 도구도 그 도구의 사건 이름으로 같은 시점에 겁니다.

| 시점 | 하는 일 |
| --- | --- |
| 세션이 시작될 때 | 지침을 세션에 넣습니다. 그 세션의 모델과 터미널을 적어 둡니다. `muwi run`으로 뜬 세션이면 맡은 노드에 붙입니다 |
| 사람이 말을 걸 때, 에이전트가 말을 끝낼 때 | 세션이 일하는 중인지 다음 말을 기다리는지 적어 둡니다 |
| 세션이 끝날 때 | 세션이 끝났다고 적어 둡니다 |
| 서브에이전트가 시작하고 끝날 때 | 어느 서브에이전트인지와 그때 하던 노드를 기록합니다 |
| skill을 읽은 뒤 | 누가 어떤 skill을 읽었는지와 그때 하던 노드를 기록합니다 |
| 서브에이전트가 셸 명령을 실행하기 전 | 그 명령이 `muwi node <id> start`면 그 서브에이전트가 시작한 것으로 기록되게 합니다. 명령을 막거나 묻지는 않습니다 |

파일을 고치기 전에는 훅을 걸지 않습니다. muwi가 업데이트돼 지침이 바뀌면 그 세션의 다음 `muwi` 명령 출력에 새 지침이 붙습니다.

훅은 실패해도 세션을 멈추지 않습니다. 오류는 `~/.muwi/.hook-errors.log`에 남깁니다.
