# 작업 계획과 진행 기록

작업을 맡은 세션이 이번 작업을 어떻게 진행할지 스스로 정하고, 그 계획과 진행을 `muwi`로 적는다.
사람은 이 기록을 Herdr 앱의 그래프로 보면서 지금 무슨 일이 일어나는지 확인하고, 결과가 이상하면 기록에서 원인을 찾는다.

`muwi`는 적어 두기만 한다. 순서를 막지 않고 다음 할 일을 정해 주지 않는다. 어떤 노드를 둘지, 어떤 skill을 쓸지, 세션을 더 띄울지는 맡은 쪽이 판단한다.

## 계획 쓰기

파일을 고치는 작업을 맡으면 첫 수정 전에 계획을 적는다. 질문에 답하기, 조사만 하기, 오타처럼 한 곳만 고치는 일에는 만들지 않는다.

계획을 적지 않은 세션이 파일을 고치려 하면 훅이 알려 준다. 계획을 적을 일이면 적고, 아니면 `muwi skip "<이유>"`로 계획 없이 진행한다고 밝힌 뒤 다시 수정한다.

```sh
muwi plan --work shop-web-PROJ-123 --request "PROJ-123 작업해줘" '{
  "title": "상품 목록에서 상품명을 누르면 상세로 이동",
  "nodes": [
    { "id": "read",   "title": "티켓·기획 읽기" },
    { "id": "branch", "title": "브랜치 준비",    "after": ["read"] },
    { "id": "impl",   "title": "클릭 이동 구현", "after": ["branch"] },
    { "id": "check",  "title": "화면으로 확인",  "after": ["impl"] },
    { "id": "pr",     "title": "PR 올리기",      "after": ["check"] }
  ]
}'
```

- `--work`는 작업 이름이고 작업 폴더(`~/.muwi/<이름>/`)의 이름이 된다. `<저장소>-<작업키>`로 짓는다 (`shop-web-PROJ-123`, `shop-web-pr-58`). 작업키는 티켓 키, PR이면 `pr-<번호>`, 둘 다 없으면 짧은 영문 요약이다. 저장소를 아직 모르면 작업키만 쓴다.
- `--request`에는 사용자가 시킨 말을 그대로 넣는다.
- 노드는 **사람이 그래프에서 읽고 무슨 일인지 알 수 있는 덩어리**로 나눈다. 이번 작업에 실제로 필요한 것만 적는다. 작은 작업이면 두세 개로 충분하다.
- `after`는 그 노드보다 먼저 하는 노드다. 동시에 해도 되는 노드는 같은 `after`를 주면 그래프에서 나란히 놓인다.
- 확인이 필요한 일(검증, 화면 확인)과 사람의 결정이 필요한 일은 노드로 드러낸다. 그래프에서 보이는 것만 사람이 챙길 수 있다.
- 긴 JSON은 `--file <경로>`나 표준 입력(heredoc)으로 줘도 된다.

이어가는 요청("아까 그거 리뷰 달렸어")이면 새로 만들지 않고 `muwi status`로 기존 작업을 찾아 `--work <이름>`으로 이어 간다. 필요한 노드는 `muwi add`로 붙인다.

## 진행 적기

| 언제 | 명령 |
| --- | --- |
| 노드를 시작할 때 | `muwi node <id> start` |
| 노드를 끝낼 때 | `muwi node <id> done "<결과 한 줄>"` |
| 사람의 결정이 필요해 멈출 때 | `muwi node <id> wait "<물어볼 것>"` 그리고 사용자에게 묻는다 |
| 스스로 풀 수 없게 막혔을 때 | `muwi node <id> block "<이유>"` |

- 끝낸 노드를 다시 해야 하면(검증에서 걸려 다시 구현) 같은 노드를 다시 `start`한다. 2회차로 기록된다. 되돌아가는 선을 그리지 않는다.
- 결과 한 줄에는 다음 사람이 알아야 할 것을 적는다 ("요구사항 2건, 미정 1건", "커밋 a1b2c3d").
- 읽은 skill은 적지 않는다. 훅이 자동으로 기록한다.
- 승인을 기다리는 동안에는 그 노드를 `wait`로 둔다 ([지킬 것](#지킬-것)).

## 계획 바꾸기

진행하다 계획이 달라지면 바로 고쳐 적는다. 이유를 꼭 남긴다. 나중에 "왜 이렇게 됐지"를 볼 때 가장 먼저 읽는 줄이다.

```sh
muwi add nourl "URL 없는 행 처리" --after impl --before check --why "상세 URL이 없는 연수원이 있음"
muwi remove check --why "화면이 바뀌지 않는 변경이라 화면 확인이 필요 없음"
muwi plan --why "요구사항이 두 화면으로 늘어남" '<새 계획 JSON 전체>'   # 크게 바꿀 때. 같은 id의 노드는 상태를 잇는다
```

사용자가 바꾸라고 한 것이면 `--human`을 붙이고 그 말을 이유에 적는다 (`--why "화면 확인 전에 lint부터 돌리라고 함" --human`).

## 다른 세션에 노드를 맡길 때

세션을 더 띄울지는 맡은 쪽이 정한다. 띄우는 방법은 그 도구의 설명서를 따른다 (Herdr 앱은 `hc --skill`, Claude Code는 서브에이전트). 맡길 때는 그 세션이 이 대화를 모른다는 점을 기억하고, 지시에 아래를 넣는다.

- 작업 이름과 노드 id. 그 세션이 직접 시작과 끝을 적는다
- 작업 위치: 저장소·worktree의 절대 경로와 브랜치. 이 경로 밖은 수정하지 않는다
- 할 일과 범위, 읽을 문서(티켓·기획서 링크, 작업 폴더의 파일 경로)
- 결과를 어디에 남길지 (작업 폴더의 파일)
- 하지 않을 것: push, PR 생성, PR 댓글, Jira 변경

```sh
muwi node impl start --work shop-web-PROJ-123     # 맡은 세션이 처음 한 번은 --work를 붙인다
muwi node impl done "커밋 2개"
```

맡은 세션은 계획을 새로 만들지 않는다. 맡은 노드만 적는다. 계획을 바꿔야 하면 맡긴 세션에 알린다.

## 지킬 것

순서와 방법은 맡은 쪽이 정하지만, 아래는 정해져 있다.

- **작업 위치**: 현재 checkout의 브랜치와 작업 트리를 바꾸지 않는다. 새 브랜치를 만들거나 다른 브랜치로 바꿔야 하는 작업은 저장소 밖 worktree에서 한다. 사용자가 위치를 지정하면 따른다.
- **작업 폴더**: 작업하면서 남기는 파일(요구사항 정리, 계획 표, 리뷰 결과, 스크린샷)은 `~/.muwi/<작업>/`에 둔다. `$TMPDIR` 아래는 쓰지 않는다. 오래 안 쓴 임시 파일은 지워져서 판단 과정을 되짚어 볼 수 없게 된다.
- **확인은 독립적으로**: 구현을 마친 변경은 구현 과정을 모르는 세션이 확인한다. 확인하는 세션에는 요구사항과 계획만 넘기고 구현 과정의 설명은 넘기지 않는다. 다시 확인할 때도 이전 지적을 모르는 새 세션을 쓴다.
- **사람에게 물을 때**: 그 노드를 `wait`로 적고, 에이전트의 질문 도구(Claude Code는 `AskUserQuestion`)로 묻는다. 글로만 "승인 필요"라고 쓰고 턴을 끝내면 끝난 세션으로 보여 사람이 놓친다. 결정이 필요한 항목만 선택지로 넣고 추천안을 첫 선택지에 둔다.
- **되돌릴 수 없는 행동**: push, PR 생성, PR 댓글, Jira 변경은 사람이 승인한 뒤에 한다.
- **끝난 것만 끝났다고 적는다**: 맡긴 세션이 끝났다는 것만으로 완료로 보지 않는다. 결과 파일과 `git log`·`git status`·diff를 직접 확인한다.
- **남겨 둔다**: 사용자가 요청하지 않으면 만든 세션과 worktree를 정리하지 않는다. 판단 과정을 볼 수 있어야 한다.

## 보기

```sh
muwi status          # 작업 목록. 사람을 기다리는 작업이 위
muwi show <작업>     # 노드, 걸린 시간, 맡은 세션, 읽은 skill, 계획이 바뀐 이유, 문제 표시
```

## 지난 작업의 문제를 진단할 때

사용자가 "브랜치 이름이 틀렸네, 왜 그랬는지 봐줘"처럼 물으면 추측하지 말고 기록을 본다.

1. `muwi show <작업>`으로 그 일이 일어난 노드를 찾는다. 사용자가 짚은 곳은 `muwi flag <id> "<무엇이 문제였는지>"`로 표시해 둔다.
2. 그 노드에서 무엇이 있었는지 읽는다.
   - **읽은 skill**: 그 노드를 하는 동안 읽은 것. `이미 읽은 상태`는 같은 세션이 앞에서 읽어 내용을 갖고 있다는 뜻이라 다시 부르지 않은 게 정상이다. 둘 다 없으면 그 세션은 그 skill 없이 일한 것이다.
   - **계획이 바뀐 기록**: 그 노드가 왜 생겼고 왜 없어졌는지.
   - **회차와 걸린 시간**, 결과 한 줄.
3. 원인이 어느 층인지 가른다.

| 기록에서 보이는 것 | 고칠 곳 |
| --- | --- |
| 필요한 skill을 읽지 않았거나 엉뚱한 노드에서 읽었다 | 그 skill의 `description` (언제 읽어야 하는지가 드러나게) |
| skill을 읽었는데 규칙을 잘못 적용했다 | 그 skill의 내용 |
| 계획 자체가 이상했다 (확인 노드가 없다, 사람에게 물을 걸 묻지 않았다) | 세션이 시작될 때 넣는 지침 (muwi의 `hooks/instructions.md`) 또는 이 skill |
| 하면 안 되는 일을 했다 | 훅 |

4. 고칠 곳과 고칠 내용을 사용자에게 제안한다. 승인하면 그 skill이나 지침이 있는 저장소에 수정 PR을 만든다. skill이나 지침을 승인 없이 고치지 않는다.

기록으로 알 수 없는 것도 있다. skill을 읽고도 무시했는지, 읽지 않았지만 맞게 했는지는 보이지 않는다. 그럴 때는 결과물(커밋, 화면)을 직접 확인한다.

## 주의

- `plan.json`과 `events.jsonl`을 직접 고치지 않는다. `muwi`로만 적는다.
- `muwi` 명령이 없으면 기록 없이 평소대로 진행하고, 설치가 필요하다고 한 번 알린다.
- 사용자가 터미널에서 `muwi`를 쓰거나 Herdr 앱에서 그래프를 보고 싶어 하면 `muwi setup`을 실행한다. 터미널용 명령과 그래프 칸을 넣는다. 실행 전에 무엇을 넣는지 알린다.
- 기록은 일을 대신하지 않는다. 노드를 끝냈다고 적기 전에 실제로 끝났는지 확인한다.
